# 04. 数据库设计

> 文档编号：04
> 上级：[需求与开发规范总纲](./README.md)
> 关联：03、05、07~12、17、18、20
> 说明：本文件为**全局数据库约定与表清单**；各表的完整字段定义随对应功能模块文档给出（`07`~`12`、`20`）。
> **字段为何存在**：每张新增表、每个扩展字段都必须能指向 `18` §3 的口径 ID 或 §9 的落位对照；无口径来源的字段不得建列（`18` §7「禁止无源口径」）。

数据库共分三类表：**① 框架系统表 `sys_*` / `gen_*`；② 原库冻结业务表 `t_*`；③ 各模块新增表。**

### 2.1 冻结硬约束（不可协商）

- 上述 8 张表**禁止 `ALTER`**：不加列、不改类型、不改字符集、**不加索引（含唯一索引）**、不重命名。依据：`08` §7、`07` §8、`18` §7 第 5 条（`17` 决策 42）。
- **禁止**为绕过上述约束而新建「替代表」并迁移数据；**一切字段增量走 §5.1/§5.2 的 1:1 扩展表**（`_ext` 后缀）或本文件已登记的新表。
- **一号制（`18` F5）只能在应用层实现**：`t_member.fileNumber` 现状为 `varchar(32) DEFAULT NULL` **且无唯一约束、种子数据多为 NULL**，既不能补列也不能加唯一索引，故唯一性由应用层校验 + 扩展表唯一索引承载（见 `17` 决策 41）。
- **订单状态扩展只能在扩展表**：`t_order.orderStatus` 为 `varchar(8)`，仅承载「已预约 / 未到诊 / 已到诊」三值，**不足以表达 `18` C4 的报告级 7+2 状态链**；原列保持不动且继续按原语义读写，新流程状态落 `t_health_order_ext.flow_status`（见 §5.2、`17` 决策 36）。
- 冻结表**物理删除**（无 `del_flag`），逻辑删除只适用于新增表（`17` 决策 8）。

> 字段定义见 `legacy/backend/health.sql`，本文档对应模块章节复述关键点（含驼峰列名与 `reservations` 可空的注意项）。
>
> **数量对账**：`health.sql` 共 15 张表 = 上表 8 张冻结业务表 + 7 张原 RBAC/用户表（`t_user`、`t_role`、`t_permission`、`t_menu`、`t_role_menu`、`t_role_permission`、`t_user_role`）。后者按 `17` 决策 10 **废弃**、改 `sys_*`，不在冻结表范围内。
>
> **现状（2026-10-22 更新）**：`docs/sql/01-schema.sql`（建表）与 `docs/sql/02-seed.sql`（种子）已存在且幂等，8 张冻结表已在 `192.168.20.130/xfjk` 建出并导入种子，回查通过（`17` 决策 25、任务 #20~#21）。`t_health_*` 新增表**尚未建**，随各模块开发按 §5 逐批入库。

## 4. 新增表约定（强制）

新增表统一遵守（见 `03` §2.2）：

1. 命名 `t_health_<实体>` 或 `<模块>_<实体>`（全小写 + 下划线），表名简洁达意。
2. 主键：`id BIGINT`，**雪花 ID**（`@TableId(type = IdType.ASSIGN_ID)`）。
3. 审计字段（框架 `BaseEntity`）：`create_dept`、`create_by`、`create_time`、`update_by`、`update_time`。
4. 逻辑删除：`del_flag CHAR(1)`（`0` 存在 / `2` 删除）+ `@TableLogic`。
5. **不加 `tenant_id`**（不使用多租户）。
6. 时间用 `datetime`（`LocalDateTime`）；日期用 `date`（`LocalDate`）。
7. 外键：**应用层维护逻辑关联，不建物理外键**（与框架一致）。
8. **1:1 扩展表（后缀 `_ext`）专则**：用于给冻结表补字段，主键仍为自身雪花 `id`，另设关联列（如 `checkitem_id INT`）并**在本表上建唯一索引 `uk_<关联列>`**（唯一索引建在新表上，不违反 §2.1 对冻结表的禁令）；扩展表**不得冗余冻结表已有列**；冻结表行删除时扩展行由应用层同事务清理。
9. 枚举与状态值**不得写魔法数**：可配置阈值/线值落 `sys_config` 或专用配置表（`18` A13），代码读取配置项。
10. 金额/价格沿用冻结表原类型（`float`）时**不得用于新表**；新表如需数值精度用 `decimal(10,2)`。

## 6. 主键与关联说明
- 冻结表主键 `Integer`，新增表主键 `Long`（雪花）。跨类型关联时以**逻辑 id** 关联（如 `member_id BIGINT` 关联 `t_member.id INT`），应用层转换，不建物理外键。
- **扩展表（`_ext`）的关联列保持与被扩展冻结表主键同类型**（如 `t_health_checkitem_ext.checkitem_id` 为 `INT` + 唯一索引），便于直接 join，不做类型转换。
- 会员相关新表以 `member_id` 关联 `t_member.id`。
- 评估/干预/报告以 `member_id` 关联会员；问卷/量表内部以 `questionnaire_id`/`question_id` 关联。
- 报告明细 `t_health_report_item.checkitem_id` **可为空**：允许录入不在 `t_checkitem` 字典内的外部结果（如解析出的历史报告项目），为空时以 `item_name` 展示。

## 7. 初始化与迁移脚本（强制）
- 分两个**幂等**脚本：`schema`（建表）与 `seed`（种子），可重复执行。**现状**：`docs/sql/01-schema.sql` + `docs/sql/02-seed.sql` 已存在（8 张冻结表 + 种子），新增表随各模块开发**追加到 `01-schema.sql` 末尾**，不新开脚本文件。
- 脚本**只允许新增表**；禁止改动冻结表 `t_*` 结构；禁止在生产库直接 DDL。
- 种子含：`sys_*` 基础数据、`health:*` 菜单与权限点、业务字典、示例账号/会员。
- **本期新增的种子必备数据**（缺了功能不可验收）：
  1. 量表题库与因子/阈值（`18` A1~A13，含 `18` A7 两个官方算例作为单元测试基线）；
  2. 危急值默认线（`18` D4，标注为**可配置默认值**，见 `17` 待确认 10）；
  3. 禁忌规则表（`18` E1~E9）；
  4. 结论词库与处理意见模板初始集（`18` F9）；
  5. 国标随访表单字典（`18` B3~B8 的值域）。
- 脚本规范详见 `03` §13；表清单以本文件 §5 为准，命名 `t_health_<实体>`。

## 8. 验收
1. 初始化脚本可建出全部 `sys_*` 框架表 + 原 8 张业务表 + §5 登记的全部新增表（含 4 张 `_ext` 扩展表与 §5.7 团检 9 张表）。
2. 新增表含审计字段、逻辑删除、雪花主键，符合 §4 约定；`_ext` 表的关联列带唯一索引。
3. 各模块文档中的表清单与本文件 §5 一致，无重名/遗漏。
4. **冻结表结构在 MySQL 中与 `legacy/backend/health.sql` 逐列一致**：执行 `SHOW CREATE TABLE` 比对 8 张表，列数、类型、索引均无变化（验证 §2.1 未被违反）。
5. 每张新增表可在文档中找到其口径 ID（`18` §3 的 A~H 之一）或明确的模块用途，无「建了但没人用」的表。
