## 1. 文档约定

### 1.1 优先级
发生冲突时：**本目录文档 > 既有代码习惯**。
其中口径冲突另有专则：**`18` §3 的口径登记表 > 功能文档中的叙述**（功能文档只引用口径 ID，不复述阈值；两者不一致时以 `18` 为准并回改功能文档）。

### 1.2 命名与编号约定
- 功能文档编号 `06`~`13` 与 §2.3 模块一一对应；`20-团检管理` 为本期新增模块的文档编号。
- 决策编号 `17` §1 的 1~46：其中 26~35 与 `18` §5.2 的 `D-26`~`D-35` **同号对应**，不得错位。
- 口径编号 `18` §3 的 A~H 组（如 `A10`、`C4`、`H12`）：功能文档写作「按 `18` C4 判定」，不得抄录数值。

### 1.3 术语表
| 术语 | 含义 |
|---|---|
| 检查项（CheckItem） | 一项具体的体检项目（如身高、白细胞计数） |
| 检查组（CheckGroup） | 若干检查项的集合（如血常规） |
| 套餐（Setmeal） | 若干检查组的集合，面向会员售卖 |
| 预约设置（OrderSetting） | 某日期开放的可预约名额 |
| 会员（Member） | C 端用户（来自微信/手机号），系统服务对象 |
| 订单（Order） | 会员对某套餐的预约记录 |
| 到诊（Visit） | 会员按预约日期到院登记的动作；在双层状态机中对应报告级流程状态的一个环节（口径见 `18` C4） |
| 档案号 | 贯穿会员历次体检的唯一编号；因 `t_member` 冻结禁加列，**仅应用层实现**（`17` 决策 41） |
| 体检号 | 一次体检的流水编号，粒度为「一次到检」，与档案号一对多 |
| 团检单位 | 批量送检的法人/组织，团检四级模型的第一级 |
| 团检批次 | 单位的一次集中体检任务（任务计划书），可多份 |
| 团检分组 | 批次内按性别/年龄/婚姻等自动划分的受检者组，每组挂一个套餐 |
| 备单 | 为团检批次按分组批量生成订单的动作 |
| 项目级状态 | 单个检查项的检查结果状态（未检/已检/待查/弃检/延期），口径见 `18` C1 |
| 报告级流程状态 | 一次体检在业务流水线上的位置（已预约→已到诊→检查中→待总检→已总检→已打印→已发放），口径见 `18` C4 |
| 分检 / 科室小结 | 各科室完成本科目检查后填写的科室结论 |
| 主检 / 总检 | 汇总全部结果、给出体检结论与医学建议的岗位与动作 |
| 三级质控 | 科室自查 → 主检审核 → 终审签发；总检未撤销前各科室不得改结果（`18` C8~C10） |
| 危急值 | 需立即通知处置的检验/检查结果，触发登记 + 通知 + 处置留痕（`18` D4~D7） |
| 重大阳性 | 需重点告知的阳性发现，总检时自动弹框且处置内容跨医生可见（`18` D8~D9） |
| 弃检 | 受检者或科室原因未完成的检查项，需登记原因并可统计 |
| 延后补检 | 因经期、妊娠等禁忌暂不做、改期补检的处置档 |
| 结论词 / 建议模板 | 知识库三层字典中的可维护词表，总检时可选用并自动带出处理意见（`17` 决策 40） |
| 健康档案 | 会员在平台的健康数据总集（基本信息 + 动态信息 + 病史 + 报告 + 评估） |
| 体检报告（Report） | 一次体检的结构化检查结果 + 附件（PDF/图片） |
| 健康评估 | 通过问卷/量表对会员健康状态进行量化评测（心理测评、中医体质、指标等） |
| 量表（Scale） | 标准化的评估问卷（如 SCL-90、中医体质九型） |
| 问卷引擎 | 可配置题目/选项/评分规则，支撑多种量表与自定义问卷 |
| 评估建议 | 依据评估结果自动或人工给出的健康建议 |
| 人群分类 | 按评估/标志将会员归入不同群体（用于干预与统计） |
| 干预方案（Plan） | 针对会员制定的一套健康管理措施（运动/膳食/随访等） |
| 健康方案 / 模板 | 可复用的干预方案模板 |
| 随访日记 | 对会员随访过程的记录 |
| 知识库 | **三层可维护字典**：结论词库 + 建议/处理意见模板库 + 疾病与健教知识库（形态重定义见 `17` 决策 40，`11` 按此重写） |
| 工作台 | 管理后台首页，聚合今日业务数据与平台概况 |
| 后台（B 端） | 供健康管理机构员工使用的管理后台 |
| C 端 | 供会员使用的移动端（H5） |

## 2. 项目概述

### 2.1 背景
原项目「传智健康」为 Dubbo + Zookeeper 的 SOA 老系统（Spring5 / MyBatis3 / JDK8 / 全 XML），仅实现了「登录 + 预约」两三个功能，但配套 Axure 原型（`manage/`）与 C 端原型（`weixin/`）已勾画出一套完整的**健康管理系统**（7 大后台模块 + C 端 6 入口）。

本项目做**学习型全重写**，采用现代分布式友好技术栈（RuoYi-Vue-Plus）从零搭建，并以 AI 大模型全栈开发。功能范围与字段口径以 `18` 的来源分级（L1 国标/行标 → L2 政府采购功能参数 → L3 三甲实操规范）为依据，**任何阈值、状态枚举、判定规则只允许引用 `18` §3 的口径 ID，不得在功能文档自拟**；范围变更记录见 `17` 决策 26~46。

### 2.2 目标
- 交付可运行的健康管理平台：**管理后台（B 端，8 模块）+ 会员移动端（C 端）**。
- 技术栈现代化、工程规范统一、代码可维护、可测试。
- 一套业务内核（模块化单体）同时服务 B 端与 C 端 API。
- 修正原项目全部已知缺陷（见 `15` §6、`16`）。

### 2.3 业务范围（本期）

平台由 **8 个后台模块 + 1 组统计分析 + 1 个 C 端**构成：

| # | 模块 | B 端（管理后台） | C 端（移动端） | 文档 |
|---|---|---|---|---|
| 1 | 工作台 | 今日预约/执行/评估汇总、平台概况 | — | `06` |
| 2 | 会员管理 | 会员档案、动态信息、病史、报告上传与结构化结果、危急值登记、会员统计 | 健康档案查看 | `07` |
| 3 | 预约管理 | 预约设置、预约列表、到诊登记、双层状态机、禁忌校验、套餐/检查组/检查项 | 套餐浏览、预约下单 | `08` |

### 2.4 角色
| 角色 | 说明 | 端 |
|---|---|---|
| 系统管理员 | 全部权限，含系统设置 | B 端 |
| 健康管理师 | 业务操作权限（会员/预约/团检/评估/干预/知识库/统计） | B 端 |
| 体检医师（科室） | 本科目结果录入与科室小结、弃检登记；总检未撤销前不得改已提交结果 | B 端 |
| 主检医师 | 总检、结论与建议、异常打回、三级质控中的审核与签发 | B 端 |
| 会员 | 使用 C 端功能，登录后查看自己的档案/报告/评估/干预 | C 端 |

> 角色与权限基于菜单×按钮模型，见 `05`；体检医师/主检医师为 `17` 决策 36（三级质控链 `18` C8~C10）新增的岗位划分，本期以角色 + 数据权限实现，不引入工作流引擎。

### 2.5 非目标（本期不做，YAGNI）
- 不做**企业团检的费用结算**：团检本身本期做（见 §2.3 模块 8），但**不含**收费结算、公费限额、公费超额转自费、发票与单位对账（`17` 决策 26、`18` §5.2 D-26/H12）。
- 不做**在线支付**（预约免费，无支付模型）——含「预约金 + 到店尾款」模式（`18` §5.2 D-27）。
- 不做**排队叫号、智能导检、导检屏、自助机、人脸识别**（`18` §5.2 D-28；其数据质控思路 D-28 中 `18` E13 单独吸收）。
- 不做**体检工作站（PACS/LIS 设备对接）与检验结果自动回传**，以报告文件解析 + 人工录入替代（`18` §5.2 D-30）。
- 不做**职业健康检查**（职业禁忌证、疑似职业病结论），结论枚举仅取 `18` F14 前三项（D-31）。
- 不做**入职/入学体检禁查乙肝两对半的下单硬校验**，仅作为 `11` 知识库一条可配规则（`18` E10、D-29）。
- 不做**多机构 / 多城市 / 集团化多院区共享库**（单一机构，D-32）。
- 不做**微服务拆分**（采用模块化单体，保持可拆分边界；不引入 MQ/注册中心/网关，D-33）。
- 不做**设备与穿戴数据接入**（CGM/AGP、体脂秤、手表），档案仅留指标录入入口（D-34）。
- 不做**微信模板/订阅消息推送**，本期仅站内提示（可选 SSE），短信走模拟实现（D-35）。
- 不做低代码工作流引擎（不使用 RuoYi-Vue-Plus 的 WarmFlow 工作流；不使用多租户）。
- 不重写原库已冻结表结构（`t_*` 8 张表**禁止 `ALTER`/加列/加索引**）；所有一切字段增量走 `t_health_*` 扩展表或新表（`17` 决策 42、`04`）。

## 3. 交付形态
- 后端：以 **RuoYi-Vue-Plus 5.6.2** 为底座、本项目自行升级至 **Spring Boot 4.1.1 / JDK 25** 的 Maven 多模块工程（版本真值见 `02` §6，升级批准见 `17` 决策 20）。
- 前端：管理后台 `xfjk-web`（**plus-ui 工程化 SPA**：Vite 7 + Vue 3.5 + TypeScript + Element Plus，`17` 决策 47；旧的「静态 HTML + Vue 2 + Element-UI、无构建」形态由决策 21 确立、已被本决策推翻）；C 端 `xfjk-app`（uniapp 3 + Vue 3 + TS）。形态说明见 `03` §9.1、`13`、`19`。
- 部署：Docker Compose 本地起 MySQL8 / Redis7 / MinIO（见 `02`）；前后端各自容器化，加入 `xfjk-net` 共享网络。
