### 2.2 登录态模型（机制已实测，不靠猜）

- 框架 `UserType` 枚举含 `SYS_USER("sys_user")` 与 **`APP_USER("app_user")`**；`LoginUser.getLoginId()` 返回 `userType + ":" + userId`（`LoginUser.java:138-146`）。
- ⇒ C 端登录时 `loginId = "app_user:{t_member.id}"`，后台为 `"sys_user:{sys_user.id}"`，**同一套 Sa-Token 空间内天然不互通**，这就是 `05` §4.1「不同 loginType 避免串端」的落地方式。
- C 端接口取会员 id 的唯一方式：`LoginHelper.getUserId()`（在 `app_user` 登录态下即 `t_member.id`）；越权判定前还须校验 `LoginHelper.getUserType() == UserType.APP_USER`（`LoginHelper` 实测提供这两个方法）。
- **禁止**从请求体/查询串接收 `memberId`（唯一来源 = token，`05` §7 第 2 条；`19` 旧版该约束已并入 `05` §7，现行 `19` 无对应章节）；**禁止**用 `t_member.phoneNumber` 反查他人数据。
- 请求头：`Authorization: Bearer {accessToken}`（`LoginVo.accessToken`，`05` §4）。

### 2.3 响应结构

统一 `R<T>` = `{code,msg,data}`（`03` §3）。分页沿用框架 `TableDataInfo<T>` = `{total,rows,code,msg}`。C 端列表页一律用 `pageNum`/`pageSize`，默认 `1`/`10`，资讯与套餐列表允许 `pageSize=6`（首页推荐位）。

## 5. 关键流程

### 5.1 登录

```
P01 输入手机号 → H15 格式校验
  → POST /app/sms/login（后端限流 60s，`05` §7；开发环境日志出码）
  → 输验证码 → POST /app/auth/login {clientId=428a…, grantType=sms, phone, smsCode}
  → 200: accessToken → uni.setStorageSync('token') → reLaunch P02（或 redirect 回跳）
  → 2001: toast「验证码错误或已过期」，保留手机号
  → 13001: toast「获取太频繁，请稍后再试」，倒计时禁用
```

### 5.2 预约下单（UI 顺序 ≠ 服务端事务顺序，R4）

| UI 步骤 | 前端动作 | 后端动作 |
|---|---|---|
| 1 | P05 填体检人 + 四维 | 本地即时校验（H13/H15、必填） |
| 2 | 选 `orderDate` | `POST /app/orders/check-date` ⇒ `5001`/`5002` |
| 3 | 自动取须知 | `POST /app/orders/forbid-preview` ⇒ 三档分流（§5.3） |
| 4 | `获取验证码` | `POST /app/sms/order`，键 `health:sms:order:{phone}`，5 分钟一次性（`05` §6） |
| 5 | 输 `smsCode` 点提交 | `POST /app/orders/check-code` 可省（预检），**真正消费在步骤 6** |
| 6 | — | `POST /app/orders` 事务内按 `08` §5.3 步骤 1~9 全量执行 |

服务端事务（照 `08` §5.3，一步不可省）：验证码 → 名额 → 重复预约（`5003`）→ 姓名+身份证识别/注册会员 → 禁忌校验 → 插 `t_order` + `t_health_order_ext`(`flow_status=已预约`) → 条件更新 `reservations`（影响 0 行回滚 `5002`）→ 写 `t_health_order_log` → 提交。
前置事实：`t_order` 对 `t_member`/`t_setmeal` **有物理外键**（`SHOW CREATE TABLE`），故必须先落会员行再插订单。
禁止：前端用本地判断替代任一步（`13` 旧 §6「禁止假校验」保留）；`localStorage` 缓存 `smsCode`；把 `setmealId` 从 URL 参数直接信任（须后端复查套餐存在）。

### 5.3 禁忌三档的 C 端处置（`18` E13、`08` §5.3 步骤 5）

| `action` | 语义 | C 端处置 |
|---|---|---|
| `0` 拦截 | 命中 `hits[]` | **禁用提交按钮**，逐条展示 `tipText` + 涉事项目名，给「调整套餐」与「改期」两个出口；提交仍返回 `5009` |
| `1` 提示 | 命中 `warns[]` | 在 P06 须知内列出，勾选「我已知晓」后放行；文案写入订单备注（`08`） |
| `2` 延后补检 | 命中 `delays[]` | 弹窗「建议延后补检」，用户二次确认 → 请求体带 `confirmedDelay=true` 放行并记 `postpone` 候选；拒绝 → 停留当前页 |

文案必须来自后端 `tip_text`，**禁止前端硬编码医学结论**（`11` §10 同源约束）。

### 5.4 我的预约：改期与取消

- 改期：仅 `flow_status=已预约` 可发起；目标日期走 `check-date`；服务端按 `08` §5.4 **先目标日 +1 再原日 -1**，失败整体回滚 `5002`；改期后禁忌重算，`拦截` 级返回 `5009` 且**不改变**原预约。
- 取消：必填 `reason`；成功后名额回退（服务端 `GREATEST(...-1,0)`，`08` §5.6）；`已到诊` 及之后 C 端不提供取消入口（须后台撤销，返回 `5006`）。

### 5.5 评估作答

分屏一题、进度 `1/N`；`single` 选中即跳下一题，`multi` 需点「确认」；`text` 题限 500 字。草稿只存本地（`uni.setStorageSync`，键 `assessment:{questionnaireId}:draft`），提交前不清除。提交体：`{questionnaireId, answers:[{questionId, optionIds[], textValue}]}`（结构同 `09` §6.3）。提交按钮加防重复（`09` `7010` + `@RepeatSubmit`，`03` §6）。中途退出再次进入时若已有 `submitted/scored` 记录 ⇒ 直接跳 P18 结果页。

### 5.6 报告只读与附件

P15 全部只读。附件下载走 `GET /app/reports/{id}/file` 拿 OSS 地址，用 `uni.downloadFile` + `uni.openDocument`；小程序端需在后台配合法域名（本期未配 ⇒ 属上线前置项，记 `17` 待确认 17）。水印与防篡改按 `18` F11 由服务端出件承担，前端**不加**水印逻辑。

## 6. 字段校验与脱敏

| 字段 | 规则 | 违反码 |
|---|---|---|
| `phone` | 11 位、`1` 开头（`18` H15，**仅格式，不声称可达**） | `400` |
| `idCard` | `18` H13 全量校验（长度/前 17 位数字/MOD 11-2 校验码/7~14 位可解析日期），服务端复核 | `6005`（`07` §7.1 身份证非法，C 端复用） |
| `birthday` | 不接受前端值，由 `idCard` 解析；解析失败 ⇒ `6005` | `6005` |
| `smsCode` | 位数与有效期取 `health:sms:code_length`、`health:sms:expire_minutes`（`12` §4.3），一次性 | `2001` |
| 同手机号重复发码 | 60 秒 1 次 | `13001` |
| `orderDate` | 晚于今天且在名额表内且 `remain>0` | `5001`/`5002` |
| `setmealId` | 套餐存在且三级结构非空 | `400` |
| `married/hasSexHistory/pregnancy` | 值域见 P05 与 `08` §2.5 | `400` |
| `answers` | 必答全覆盖、`single` 1 个选项、`multi` ≥1、选项属该题 | `7002` |
| 展示脱敏 | 非本人上下文的手机号/身份证一律掩码（手机 `138****8888`、身份证 `1101**********1234`） | — |
| 富文本 | 仅 `rich-text` 白名单标签，禁外部脚本（`11` §10） | `11009` |

`age`、`bmi`、`血压达标`等**一律服务端计算**，前端不传也不自算（`07` §2.3「不信任前端值」、`10` §4.2）。

## 8. 错误码（`MMNNN` 五位块，`03` §3 同步登记）

> 只承载「C 端展示层与开放范围」语义。预约/会员/评估/干预的业务码一律沿用 `5xxx/6xxx/7xxx/8xxx` 与 `2001/401/403`，**不得**在 C 端另开同语义码（`03` §3 分块规则）。

| code | 含义 |
|---|---|
| 13001 | 验证码请求过于频繁（同手机号 60 秒内重复发送） |
| 13002 | 会员尚未建档（无档案号或档案不存在，档案/报告/干预类页面前置不满足） |
| 13003 | 问卷未对 C 端开放（`status ≠ published` 或 `is_public ≠ 1`） |
| 13004 | 报告附件不可获取（`file_url` 为空或对应 OSS 记录缺失、不可读） |
| 13005 | 内容已下架（资讯 `status ≠ published`、疾病科普不可见） |

## 10. 验收（逐条打勾）

**工程**
1. `npm run type-check` 与 `npm run build:mp-weixin` 通过；H5 端 `http://localhost:5173` 可访问。
2. `pages.json` 已登记 P01~P10 十条路由；每条可进入且标题正确。
3. 全站无硬编码色值（除 `tokens.scss`）；导航栏主色不再是 `#1E90FF`。
4. `request.ts` 带 `ClientID`，并实现 401/403 分支；页面内 0 处裸 `uni.request`。

**认证**
5. 用 app 的 `clientId` + `grantType=sms` 登录成功并拿到 `accessToken`；用 pc 的 `clientId` 打同请求被拒。
6. 验证码一次性：第二次使用同一码返回 `2001`；60 秒内重复发码返回 `13001`。
7. 用 pc token 访问 `/app/reports` 返回 401/403（`loginId` 前缀隔离生效）。
8. 会员 A 的 token 请求会员 B 的 `orderId`/`reportId` ⇒ 403（`05` §7）。

**下单闭环**
9. P02 六宫格入口跳转正确；未登录点需登录项跳 P01 且登录后回跳原目标。
10. 套餐列表筛选（性别/年龄段）与详情的三级结构展示正确，三级数据与后台 `08` 页面同源。
11. 选到 `remain=0` 的日期返回 `5002` 且不可提交；未设置的日期返回 `5001`。
12. 拦截级禁忌命中 ⇒ 提交按钮禁用且展示 `tipText`；强绕（直接 POST）返回 `5009` 且**未占用名额**（`reservations` 不变）。
13. 提示档写入须知并在 P06 可见；延后档需二次确认才放行。
14. 成功下单后：`t_order` 新增 1 行、`t_health_order_ext.flow_status=已预约`、当日 `reservations` +1、`t_health_order_log` 有「预约」记录；并发压测同一日不超卖（条件更新生效）。
15. 同会员/同日/同套餐重复提交返回 `5003`。
16. 身份证非法返回 `6005`；`birthday` 由证号解析，与前端传值无关。
17. P07 展示 `orderId` 且**不出现** `exam_no`。

**订单后续**
18. P08 四个 tab 的 `flow_status` 归属与 §3.2 P08 表完全一致；改期成功且两日名额一增一减。
19. 取消未填原因返回 `400`；`已到诊` 后 C 端无取消入口。

**开放范围（安全）**
20. 未登录访问 `/app/orders` 列表、`/app/home`、`/app/archives` 均 401。
21. C 端接口响应中**不含**：`scale_rule`、`norm_mean`、`norm_sd`、`factor_code`（题目接口）、`ref_min`、`ref_max`、质控链时间与内部 id、`revoke_*`、`batch_id`、`report_id`、`orderStatus` 原值。
22. `is_public=0` 或 `status≠published` 的问卷在 C 端列表不可见，直接访问返回 `13003`。
23. `status≠published` 的资讯、`draft/terminated` 的方案在 C 端列表不可见；访问下架资讯返回 `13005`。
24. 公开接口返回体中无任何会员标识字段（用 `grep` 对响应样例核验）。

**依赖项（未就绪时按占位开关验收，不计失败）**
25. P11~P22 在后端模块未创建时，页面显示占位数据 + 「数据待接入」标注，且**不得**伪装成功（无静默假数据提交）。

## 11. 约束与禁止

1. C 端为独立工程 `xfjk-app`，禁止混入 `xfjk-web` 的后台页面代码或原 jQuery 代码；禁止把 legacy `com.pangzhao` 代码复制进来（只可查语义）。两端同为 Vue 3 但**工程形态不同**（后台 Vite SPA、C 端 uniapp 3），禁止跨工程直接 import 对方 `src/**`。
2. 禁止 `ALTER` 任何冻结表以「配合 C 端需求」：`t_member.password` 短（R1）、`t_member` 无唯一索引、`t_order` 无订单号（R7）都是**既定事实**，不得绕过。
3. 禁止信任前端传入的 `memberId`、`birthday`、`age`、`bmi`、`setmealId` 存在性判断、禁忌校验结果。
4. 禁止在 `xfjk-app` 引入 axios（现状无该依赖），封装只走 `uni.request` 的 `request.ts`；旧文档「走 Axios 封装」的表述作废（§12）。
5. 禁止 C 端直接调用 `/health/**` 与 `/system/**`（那是 B 端接口，带权限点校验）。
6. 禁止在 C 端下发或渲染内部判定资产（阈值、常模、规则区间、A/B 分级、质控时限、打回与撤销记录）。
7. 禁止前端硬编码医学结论文案，须知与禁忌提示一律取后端 `tip_text` / `noticeText`。
8. 禁止把验证码、token、真实凭据写入仓库；`BASE_URL` 本地临时改动不得提交（`03` §9）。
9. 禁止未登记 `pages.json` 的页面「以组件形式硬塞进路由」。
10. 下单顺序固定为 日期 → 须知/禁忌 → 验证码 → 提交，禁止跳步或用前端本地判断替代后端任一步校验。
11. 本期禁止实现微信授权登录、支付、订阅消息（见 §1.3）；`grant_type` 不扩、`sys_client` 不加行。
