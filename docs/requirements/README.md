## 阅读与使用方式

- **人类读者**：按编号 `01 → 20` 顺序阅读即可建立完整认知。
- **AI 编码代理**：先读本文（索引），再按任务**按需只读相关文档**，避免上下文浪费：
  - 涉及架构/依赖/底座/包名 → `02`
  - 涉及编码规范/返回结构/权限注解 → `03`
  - 涉及建表/字段/新表 → `04`
  - 涉及权限/登录/多端/短信 → `05`
  - 涉及某功能模块 → `06`~`13`、`20` 对应文档
  - 涉及**阈值、判定标准、计数分母** → 先查 `18` §3 A~H 口径登记表（唯一数值来源），再看功能文档怎么用
  - 涉及页面重设计/视觉规范 → `19-页面重设计`
  - 动手编码前 → 必读 `15-AI开发约束`
  - 改造原系统代码时 → 参考 `16-原系统对照与改造`
- 每个功能文档结构统一：**用途 → 数据表 → 接口清单 → 页面/交互 → 业务规则 → 验收标准 → 约束与禁止**。

### AI 使用协议（强制）
1. 动手前**必读** `15-AI开发约束与执行协议`（执行协议、铁律、精确版本、禁止清单 DENY、DoD）。
2. 任务前置：明确目标模块 / 文档编号 / 涉及的表与接口 / 验收标准；**找不到就按 `15` §0.3 确定性阶梯自行判定（技术问题零拍板），禁止臆造**；只有 `15` §0.3.2 的四类业务/风险问题才允许打断人类。
3. **只做文档已定义范围**；扩展（新表/新列/新依赖/新接口）须先获批准（见 `15` §0.4）。
4. 完成后必须给出**验证命令 + 实际输出 + 预期结果**；无证据视为未完成（见 `15` §4.2）。
5. 上下文达窗口 **80%** 时停止并汇报进度，**不默默截断**（见 `15` §0.5）。

## 全局约定

- **包名根**：`com.xinfei`；框架模块包 `com.xinfei.{common,system,generator,job,admin,...}`；业务模块包 `com.xinfei.health.<module>`。
- **统一返回**：`R<T>`（`code/msg/data`）与分页 `TableDataInfo<T>`（`code/msg/rows/total`），见 `03`。
- **权限注解**：Sa-Token 的 `@SaCheckPermission` / `@SaCheckRole`，见 `05`。
- **数据库**：RuoYi 自带 `sys_*` 系统表 + 原库 `t_*` 业务表（结构冻结）+ 各模块新增表；主键策略与字段约定见 `04`。
- **前端**：管理后台 `xfjk-web`（**目标形态** = plus-ui 工程化 SPA：Vite 7.3.2 + Vue 3.5.30 + TypeScript + Element Plus 2.13.5 + Pinia + axios，版本对锁 `v5.6.2-v2.6.2`，`17` 决策 47；**当前仓库形态**仍是 15 个静态 HTML + Vue 2 + Element-UI 2 UMD 无构建页，`css/tokens.css` 设计令牌 + `js/api.js` 统一封装——换栈**尚未实施**）；C 端 `xfjk-app`（uniapp 3 + Vue 3 + TS + vite，微信小程序 / H5 双端）。详见 `03` §9.1、`13`、`19`。
- **需求来源**：对成熟产品的真实调研，见 `18`。

## 实现现状（2026-10-22 校准）

文档定义的是目标，下列为**已核实的当前缺口**，派单时必须据此判断可执行性：

- **首个业务垂直切片已打通（2026-10-22 实测）**：`xfjk-modules/xfjk-health-appointment` 已创建，含 检查项 / 检查组 / 套餐 三实体的 Controller-Service-Mapper-Entity-BO/VO 与 `/health/checkitems`、`/health/checkgroups`、`/health/setmeals` 接口；`docs/sql/01-schema.sql`、`02-seed.sql` 已在 `192.168.20.130/xfjk` 执行，8 张 `t_*` 冻结表 + 种子数据到位；`xfjk-web` 的 `checkitem.html`、`checkgroup.html`、`setmeal.html` 三页已改调本项目接口（增删改查、差异更新、引用校验拦截均经浏览器实测取证）。
- **其余缺口仍在**：`02` §2 规划的 6 个 `xfjk-health-*` 模块建成 **1 个**；预约设置/订单、`/app/**`、评估/干预/知识库/统计侧的表与接口仍无实现；`xfjk-web` 其余页面仍调用 `.do`。该切片作为其余模块的**样板**（分层、差异更新、引用校验、错误码 `3001/3002/4001`、`TableDataInfo` 分页信封透传）。
- **但原系统完整保留在 `legacy/`**（不在 Maven reactor 内，`pom.xml` 无 `legacy` 模块，不参与构建）：

| 路径 | 内容 | 用途 |
|---|---|---|
| `legacy/backend/health.sql` | 原库建表脚本，**15 张 `t_*` 表**（`t_member`/`t_order`/`t_ordersetting`/`t_setmeal`/`t_setmeal_checkgroup`/`t_checkgroup`/`t_checkgroup_checkitem`/`t_checkitem` + 原 RBAC 6 张 + `t_user`） | `04` §2 冻结表的**唯一字段真值来源** |
| `legacy/backend/health_backend` | 原管理后台（`com.pangzhao`，`.do` 接口） | `xfjk-web` 现有 28 个 `.do` 调用的**对端实现** |
| `legacy/backend/health_mobile` | 原 C 端服务（含 `OrderController` 等） | C 端下单/查询逻辑参照 |
| `legacy/backend/health_common` / `health_interface` / `health_service_provider` / `health_job` | 原 Dubbo SOA 分层 | 业务规则与 SQL 参照 |
| `legacy/prototype/manage`、`legacy/prototype/weixin` | 原型页面 | `19` 页面重设计的原始依据 |

- **结论**：`06`~`13` 的功能需求**不是从零开发，而是从 `legacy/` 迁移重写**——旧实现是业务规则、字段语义、边界条件的可查证来源，遇到文档未写清的细节按 `15` §0.3 阶梯查：第 2 级即 `legacy/`，其后还有本仓库样板、框架源码、`15` §0.3.1 默认口径表，**走完阶梯才提问**，且只有 §0.3.2 四类允许提问。
- 迁移仍须按新规范落地（`/health/**` 接口、`sys_*` 权限、新表约定），**禁止直接复制 `com.pangzhao` 代码或把 `legacy/` 纳入构建**。
- `xfjk-web` 现有页面的 `.do` 调用属**待改造存量**，不是可用功能。
- **后台前端换栈尚未实施**（`17` 决策 47 / `02` §7 第 9 项）：文档全篇按 plus-ui SPA 形态书写，代码仍是静态页形态。派单前端任务前必须先确认该切片是否已做——若 `xfjk-web/package.json` 不存在，说明仍是旧形态，此时按文档写 Vue 3 SFC 会落不了地。
