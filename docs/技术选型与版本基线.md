## 2. 为什么是 4.1.3，不是刚 GA 的 4.2.0

事实（2026-11 核对官方渠道）：

- `4.1.3` 于 **2026-11-19** 发布，是 4.1 线最新补丁；4.1.x 世代的开源支持到 **2027-07-31**，商业支持到 2028-07-31。
- `4.2.0` 同样于 **2026-11-19** GA，属于刚发布的次世代版本。
- 4.1.3 要求 Java 17 起、**最高兼容 Java 27**，JDK 25 属官方支持矩阵内。
- Spring Cloud 适配 4.2 的 **2026.0 发布列车当时仍为 RC**（未 GA）。

据此三条理由：

1. **生态还没跟上**。本项目锁 Sa-Token 1.46.0、MyBatis-Plus 3.5.17、SnailJob、Spring Boot Admin 这一组，是在 4.1 线上验证过编译 + 测试 + 登录端到端的组合。4.2 才 5 天，第三方库对 4.2 的兼容声明基本为空白。
2. **微服务仓不能跟着跳**。同族的 xfwl / xfjy / xfjz / xfcy / xfhj 是 Spring Cloud 栈，Cloud 2026.0（配 4.2）未 GA，单方面把 xfjk 抬到 4.2 会失去统一基线，后续无法共享配置与排障经验。
3. **4.1 的支持期足够覆盖当前阶段**。到 2027-07 仍有 8 个月以上的开源支持窗口，届时再评估 4.2/4.3。

结论：**锁 4.1.3**。4.1.1 与 4.1.2 均视为过期版本，不得回退。等到 Spring Cloud 2026.0.0 GA **且** Sa-Token/MyBatis-Plus 明确声明支持 Boot 4.2，再按 §5 流程整体抬升。

## 3. 数据库：MySQL 8.4.13 LTS 定版，9.x 与 PostgreSQL 17 均不采用

### 3.1 版本格局（2026-11 核对）

- MySQL **8.0 已于 2026-04 结束常规支持**（转 Sustaining Support），现有以 8.0 为基线的项目都属待迁状态。
- 现行两条 LTS：**8.4 LTS**（支持至 2032-04）、**9.7 LTS**（2026-04 发布，支持至 2034-04）。
- **Innovation 线（26.7 / 26.10 这类日历版本号）生命周期约 3 个月**，生产禁用。
- **8.4 线当前补丁是 8.4.13**（2026-11 实测：浮 tag `mysql:8.4` 拉到的就是 8.4.13，192.168.20.88 上的共用库也由它初始化）。补丁号只能前进不能后退——MySQL 不支持用低补丁打开高补丁写过的数据目录，所以 tag 必须写死 `mysql:8.4.13`。

### 3.2 为什么定 8.4.13，而不是 9.7

1. **升级路径差一个量级**。8.0 → 8.4 是官方原地升级（换镜像、数据目录直接可用）；8.0 → 9.7 必须逻辑导出再导入，中间还要处理账号插件与字符集，属于一次数据迁移，不是一次版本调整。
2. **9.x 的默认行为变更会打到现有脚本**。9.x 默认禁用 `mysql_native_password`，老账号直接连不上；`mysql-connector-j`、备份与运维工具链都要跟着换。8.4 侧这些行为与 8.0 基本一致。
3. **8.4 的支持期覆盖部署周期**。2032-04 到期，比 9.7 少两年，但当前阶段用不到那两年；等真要跨到 9.x 时，8.4 本身的升级经验已经沉淀下来了。
4. **项目定位是稳，不是追新**。这是体检业务系统，数据库换大版本带来的收益（新特性）几乎用不上，风险却全落在迁移窗口里。

结论：**定版 8.4.13（LTS 补丁号写死）**。9.7 不作为目标版本，也不作为"以后再看"的选项——真要用 9.x 时按 §5 重新立项。

### 3.3 部署前必须做的三件事

1. 镜像 tag 写死 `mysql:8.4.13`，禁止 `mysql:8`、`mysql:8.4`、`mysql:latest` 这类浮动 tag。
2. 从 8.0 升级时先做一次全量 `mysqldump`（带 `--default-character-set=utf8mb4 --set-gtid-purged=OFF`）再换镜像，别指望换镜像就能起。
3. 连接串、`mysql-connector-j` 版本跟着 Boot BOM 走；排序规则 `utf8mb4_0900_ai_ci` 在 8.4 仍在，`docs/sql` 12 个脚本不受影响。

### 3.4 备选：PostgreSQL 17

只有 MySQL 8.4 也不满足时（例如许可/合规、特定 SQL 方言需求）才评估，且必须单独立项：

- JDBC 驱动与 URL、MyBatis-Plus 方言；
- `docs/sql` 12 个脚本 DDL 重写（`DATETIME` / `ON UPDATE CURRENT_TIMESTAMP` / `ENGINE=InnoDB` / `utf8mb4` 全要改）；
- SnailJob 与 Spring Boot Admin 的元数据库、备份与监控脚本。

**预估 3~5 人日 + 全量回归**，不在日常迭代里做。

## 4. 禁改清单（防止被回退）

以下行为一律视为**违规改动**，评审直接打回：

1. 把 `spring-boot.version` 改回 `4.1.1` / `4.1.0` / `4.1.2`，或改成 `4.2.x`（未走 §5 流程）。
2. 把 JDK 从 25 降回 21/17，或升到 26。
3. 把 Jackson 从 `tools.jackson` 改回 `com.fasterxml.jackson`。
4. 把数据库基线改回 `MySQL 8.0`，或改成 `MySQL 9.x`，或把镜像 tag 写成 `mysql:latest` / `mysql:8` / `mysql:8.4`（必须写 `mysql:8.4.13`）。
5. 在无关业务改动里顺带升降 `pom.xml` 版本段或 `package-lock.json`。
6. 把 `xfjk-web` 版本对改成非 `v5.6.2-v2.6.2` 的 plus-ui tag。

## 5. 变更流程

1. 提出变更：说明目标版本、动机、影响面（构建/运行时/中间件）。
2. 批准：由项目作者确认。
3. 落地：改代码 → 编译/测试/启动至少一项实测。
4. **回写三处**：本文 §1 表格、`docs/requirements/17-决策记录与待确认.md` 新增一条决策（含回滚代价）、`CHANGELOG.md` 记一行。
5. 提交信息用中文 `type: 简述`，正文注明"版本基线变更"。
